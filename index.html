The Agentic Loop

A normal model call is one-shot. The agentic loop is the pattern in your code that keeps calling the model, running the tools it asks for, until the task is actually done.

60-second summary
  • Four stages: compose & send → model responds → inspect stop_reason → act & feed back. Repeat.
  • The model can't run tools. It asks; your code runs them and returns results.
  • The model has no memory. Send the full history every call.
  • Exit only on end_turn. Never exit on tool_use. Never treat max_tokens as finished.
  • History order: assistant message (unchanged) → one user message with every tool_result.
  • Always put a cap on iterations.

The four stages

  1. Compose & send. First turn: system prompt, tool definitions, user request. Every later turn: the whole history again (request, every assistant reply, every tool call, every tool result).
  2. Model responds. The reply holds content blocks: text, tool_use, or both. The model cannot execute anything itself; it has no access to your systems.
  3. Inspect the response. Look at stop_reason first. Everything else follows from it.
  4. Act & feed back. If tools were requested, run them, append the assistant message and the results, and go back to stage 1.

Key idea: the loop is not a model feature. It's a pattern you write, and the messages array is the model's only memory. If something isn't in it, the model doesn't know it happened.

The stop_reason field

Every response says why the model stopped generating. Reading content before checking it is like reading an answer before hearing the question.

ValueMeaningWhat your code does
end_turn exitModel finished naturally. The happy path.Return the text and leave the loop. Make it an explicit branch so logic doesn't fall through.
tool_use continueModel wants one or more tools run. It is not done.Find every tool_use block, run each, append assistant msg + results, call again.
max_tokens handleCut off by the token budget. Output is incomplete.Continue generation, or surface an error. Never pass it on as finished. Frequent hits mean prompt, limit or task size needs changing.
stop_sequence exitHit a custom stop string you configured.Treat like end_turn; take content before the sequence. Check which one fired if you set several.
anything else defaultUnexpected, missing or malformed.Default branch: log it and exit gracefully. Never let it pass silently.

Coding agent mid-function

Hit max_tokens? Usually continue: send the partial back and ask it to pick up where it left off, then stitch the pieces.

Summarization pipeline

Hit max_tokens? Usually a hard stop and redesign the prompt or split the input.

The course covers these four. The current API can also return pause_turn and refusal; your default branch catches them.

Exam trap

"A tool result came back, so the agent is finished." Wrong. A tool result is the middle of the process. The only normal exit is end_turn with no pending tool calls, and the model should get the last word to turn raw data into an answer.

Branching on tool_use: five steps

  1. Extract every tool call. Filter response.content for type == "tool_use". Each has a name, an input object and an id. Keep the id.
  2. Execute each tool. Route the name to your function, pass the input, capture output. Run independent calls in parallel. Turn failures into structured error results instead of crashing.
  3. Append the assistant message. The full content exactly as returned, text and tool_use blocks included. Don't trim it.
  4. Append the tool results. One new user message with one tool_result block per call, each with the matching tool_use_id.
  5. Loop back. Call the model again with the updated history, under a max-iteration guard.

Root cause of most bugs: treating history as an afterthought instead of the foundation the model reasons from.

Appending tool results to history

Always a two-part operation: the assistant message first, then the tool results in a new user message. In that order, every time.

Complete agentic loop (Python)

The pattern the exam expects, with every guard. Install with pip install anthropic and set ANTHROPIC_API_KEY.

agent_loop.py
import json
from concurrent.futures import ThreadPoolExecutor
import anthropic

client = anthropic.Anthropic()
MODEL = "claude-sonnet-5-5"
MAX_ITERATIONS = 10                       # guard against runaway loops

# ---- 1. Tool definitions (what the model is told it can ask for) ----
TOOLS = [{
    "name": "get_weather",
    "description": "Get current weather for a city.",
    "input_schema": {
        "type": "object",
        "properties": {"city": {"type": "string"}},
        "required": ["city"],
    },
}]

# ---- 2. Real implementations (what your code actually runs) ----
def get_weather(city: str) -> dict:
    return {"city": city, "temp_c": 31, "sky": "humid"}   # pretend API call

TOOL_FUNCS = {"get_weather": get_weather}

def run_tool(block) -> dict:
    """Run one tool_use block and ALWAYS return a tool_result block."""
    fn = TOOL_FUNCS.get(block.name)
    if fn is None:
        return {"type": "tool_result", "tool_use_id": block.id,
                "content": f"Unknown tool: {block.name}", "is_error": True}
    try:
        output = fn(**block.input)
        return {"type": "tool_result", "tool_use_id": block.id,
                "content": json.dumps(output)}           # serialize to string
    except Exception as e:                               # never crash the loop
        return {"type": "tool_result", "tool_use_id": block.id,
                "content": f"{type(e).__name__}: {e}", "is_error": True}

# ---- 3. The loop ----
def run_agent(user_request: str) -> str:
    messages = [{"role": "user", "content": user_request}]

    for _ in range(MAX_ITERATIONS):
        response = client.messages.create(
            model=MODEL,
            max_tokens=4096,
            system="You are a helpful weather assistant.",
            tools=TOOLS,
            messages=messages,              # the WHOLE history, every time
        )

        if response.stop_reason == "end_turn":
            return "".join(b.text for b in response.content if b.type == "text")

        if response.stop_reason == "tool_use":
            # a) assistant message first, unchanged
            messages.append({"role": "assistant", "content": response.content})
            # b) find ALL tool calls, run independent ones in parallel
            calls = [b for b in response.content if b.type == "tool_use"]
            with ThreadPoolExecutor() as pool:
                results = list(pool.map(run_tool, calls))
            # c) ONE user message holding every tool_result
            messages.append({"role": "user", "content": results})
            continue                        # d) loop back

        if response.stop_reason == "max_tokens":
            raise RuntimeError("Response truncated by max_tokens; raise the limit or split the task.")

        if response.stop_reason == "stop_sequence":
            return "".join(b.text for b in response.content if b.type == "text")

        raise RuntimeError(f"Unexpected stop_reason: {response.stop_reason}")

    raise RuntimeError(f"Stopped after {MAX_ITERATIONS} iterations without end_turn.")

print(run_agent("Compare the weather in Chennai and Mumbai."))

Spot the bug

Each snippet has a mistake from this section. Find it, then open the answer.

Bug 1
response = client.messages.create(model=MODEL, max_tokens=2048, tools=TOOLS, messages=messages)
if response.stop_reason == "tool_use":
    block = next(b for b in response.content if b.type == "tool_use")
    result = run_tool(block)
    messages.append({"role": "assistant", "content": response.content})
    messages.append({"role": "user", "content": [result]})
Answer to bug 1

next(...) grabs only the first tool_use block. If the model asked for three tools, two are dropped. Use a list comprehension over all blocks and return a result for each.

Bug 2
calls = [b for b in response.content if b.type == "tool_use"]
messages.append({"role": "assistant", "content": response.content})
for call in calls:
    messages.append({"role": "user", "content": [run_tool(call)]})
Answer to bug 2

One user message per result. All results from one round belong in a single user message: messages.append({"role": "user", "content": [run_tool(c) for c in calls]}).

Bug 3
while True:
    response = client.messages.create(model=MODEL, max_tokens=2048, tools=TOOLS, messages=messages)
    if response.stop_reason == "tool_use":
        calls = [b for b in response.content if b.type == "tool_use"]
        results = [run_tool(c) for c in calls]
        return results[0]["content"]
    return response.content[0].text
Answer to bug 3

It ends the loop too early and returns raw tool output instead of feeding it back. while True has no iteration cap. And it treats max_tokens as a finished answer.

Bug 4

messages.append({"role": "assistant", "content": response.content})

Wrong order. The tool results appear before the assistant message that requested them, so the model sees results with no preceding tool call. Append the assistant message first.

Hub and Spoke Model

A central coordinator (the hub) splits a job across specialized subagents (the spokes), gives each the context it needs, and combines their results into one answer.

60-second summary
  • All communication flows through the coordinator. Subagents never talk to each other.
  • Subagents run in isolated contexts with no shared memory. Everything must be passed explicitly.
  • Every handoff: objective, context, constraints, expected output.
  • Aggregation is synthesis, not copy-paste: remove overlap, connect findings, resolve contradictions.
  • Classify errors first: transient → retry; validation → fix input; business logic → inform; permission → escalate.
  • Bad final output? Blame the coordinator first: decomposition, context, aggregation, or stopping early.

How communication flows

SpecializationEach subagent has one narrow job, so it does it more accurately.
ScalabilityWork is spread out instead of overloading one agent.
Easier debuggingSeparate responsibilities: fix one part without touching the rest.
PredictabilityCentral control avoids hidden dependencies and duplicate work.

Why isolation, not shared memory

Direct chatter or shared memory creates hidden dependencies, context pollution, duplicated reasoning and outputs influenced by state nobody passed on purpose. Isolation makes every task self-contained, predictable and reproducible.

Contractor analogy: an electrician, plumber and structural engineer each know only the briefing you give them. The coordinator is the project manager who moves information between them.

How a coordinator decomposes tasks

The coordinator works like a project manager. Subagents don't infer missing responsibilities, so anything it forgets to assign simply won't get done, no matter how good the subagents are.

  1. Understand the primary objective. What is the user actually asking for?
  2. Identify independent subtasks. Split into parts that can be handled cleanly on their own.
  3. Assign specialization. Pick the best-suited subagent for each part.
  4. Define expected outputs. Format, structure and content each subagent returns.
  5. Plan aggregation. Decide how results combine before any subagent starts.

Weak vague

"Analyze the company." sent to one subagent. It has to guess scope, depth and format.

Strong scoped

Financial performance · competitive positioning · operational risk · executive summary. Each with a clear objective and boundary.

SymptomDecomposition cause
A topic is missing entirelyNobody was assigned it
Outputs overlap heavilyBoundaries between subtasks were unclear
Synthesis lacks key infoCoordinator never requested it from a subagent

How to pass context to a subagent

A subagent receives only what's in the task you send. It can't see the coordinator's history, other subagents' work, or anything "obvious".

1. ObjectiveExactly what to accomplish.
2. ContextBackground, prior findings, IDs, data.
3. ConstraintsPolicies, limits, rules to follow.
4. Expected outputFormat and fields to return.

Bad handoff

"Continue analyzing the issue."

Which issue? What's already done? What should come back?

Good handoff

"Customer requested a refund for order #8831. Prior analysis: shipment delayed 12 days. Task: decide whether the refund policy applies. Return: eligibility (yes/no) plus an explanation."

Exam trap

If a subagent fails because information was missing, the coordinator is responsible. "Use a bigger model for the subagent" is the wrong fix.

How a coordinator aggregates results

Subagents don't coordinate their outputs, so the coordinator must synthesize: remove redundancy, connect related findings, prioritize, and structure the answer as summary → key findings → detailed evidence.

Weak aggregation

Pastes the financial, sentiment and competitor reports one after another. Reads like disconnected reports stapled together.

Strong aggregation

Leads with the main insight, links findings across reports, drops repetition, explains how results relate.

Contradictions aren't always conflicts. "Strong revenue growth" and "severe operational risk" can both be true. A strong coordinator explains how they relate (short-term success, long-term threat) instead of picking one or listing both without comment.

How a coordinator handles subagent errors

Failures are normal. What matters is classifying them first, then picking the matching recovery.

Failure typeExamplesRight responseRetry?
TransientTimeout, overloaded service, API outageRetry with exponential backoff / delayyes
ValidationMissing parameter, bad format, malformed requestFix the input or ask for clarificationafter fixing
Business logicRefund outside window, insufficient balanceSystem worked, answer is "no". Inform user, offer alternatives, escalate if neededno
PermissionAccess denied, missing credentialsEscalate to a human or higher authorizationno

A subagent should never just say "task failed". A useful error report carries the failure type, what it was attempting, any partial results, and possible alternatives.

coordinator recovery logic
import time

def handle_subagent_result(result, retry_fn, attempt=0, max_retries=3):
    if result.get("status") == "ok":
        return result

    kind = result.get("failure_type")
    if kind == "transient" and attempt < max_retries:
        time.sleep(2 ** attempt)                 # 1s, 2s, 4s backoff
        return handle_subagent_result(retry_fn(), retry_fn, attempt + 1)
    if kind == "validation":
        return {"action": "fix_input", "detail": result["attempted"]}
    if kind == "business_logic":
        return {"action": "inform_user", "detail": result["reason"],
                "alternatives": result.get("alternatives", [])}
    if kind == "permission":

Exam trap

Retrying a business-logic or permission failure is wrong. Retrying only makes sense when the environment, not the request, was the problem.

Diagnosing incomplete coordinator output

When the final answer is shallow or missing pieces, trace the orchestration step by step before blaming the model.

  1. Decomposition. Was every needed part assigned? You can't aggregate what was never produced.
  2. Context passing. Missing history, constraints or output spec → shallow or hallucinated subagent work.
  3. Aggregation. Subagents did fine, but the coordinator dropped findings or left contradictions unresolved.
  4. Premature termination. Stopped after the first tool result, after a recoverable error, or before synthesizing.

Rule of thumb: most orchestration failures come from coordinator logic, not subagent intelligence.

Task Tool and Parallel Execution

The Task tool is how one Claude (the coordinator) hands work to another Claude (a subagent). Configure it correctly, then run independent subagents at the same time.

60-second summary
  • Renamed Task → Agent in Claude Code v2.1.63. Put "Agent" in allowedTools.
  • Without it in the coordinator's allowedTools, no subagent ever runs (and nothing crashes).
  • Give every subagent an explicit tools list, and never include Agent in it.
  • Several Agent calls in one response run in parallel. Total time ≈ slowest subagent.
  • Ask one question: does any task need another's output? No → parallel. Yes → sequential.
  • Stakes-proportionate: the more irreversible the action, the more caution and confirmation.

What the Task tool is

It's the wire between a coordinator and a subagent. The subagent isn't a function call: it's a full Claude run with its own context window, tools and reasoning. The coordinator sends a brief and waits for the deliverable, like a project manager handing a spec to a contractor.

Know both names

Today "Agent" appears in tool_use and tool result blocks and is what you write in allowedTools. "Task" still appears in the system:init tools list. Detection code should match both names.

Use a subagent when…

The subtask would fill its own context window, needs tools the coordinator shouldn't have, should succeed or fail on its own, or can run in parallel.

Don't, when…

The only reason is "my prompt is getting long". Delegation adds overhead; it must pay for itself in clarity, reliability or speed.

Why coordinators need Agent in allowedTools

Claude only knows about tools registered in its context. The SDK injects the Agent tool's schema only when "Agent" is allowed. It's opt-in for two reasons: safety (subagents take real actions, so delegation shouldn't happen as a side effect) and composability (the default is the least powerful, most predictable setup).

Sequential vs parallel invocation

One question: does any task need another task's output? No → parallel. Yes → sequential. If a subagent prompt says "based on the result of the previous task", that's a dependency.

Parallel

Sequential

Parallelizing these makes the later agent hallucinate, because its input doesn't exist yet.

Programmatic Control and Hooks

Once Claude can touch real systems, you need code that checks each action before it runs and inspects each result after. Prompts guide Claude; gates and hooks enforce the rules.

60-second summary
  • A prompt gives instructions, not knowledge or guarantees. Correctness comes from architecture: grounding plus enforcement.
  • A programmatic gate is your code between Claude's tool call and its execution: allow, block or modify.
  • Interception (PreToolUse with updatedInput) silently fixes almost-right calls instead of blocking them.
  • PostToolUse runs after the tool: audit logging, enrichment, masking secrets. It can't stop what already happened.
  • Gates are preventive; post-checks are detective. Use PreToolUse for safety, PostToolUse for intelligence.
  • Hooks get the tool call as JSON on stdin and answer with JSON on stdout. Exit 2 blocks. Invalid JSON is ignored.

Why prompts alone cannot guarantee correctness

A perfect instruction still produces a wrong answer if the information behind it is incomplete. A model only has two sources: what it learned in training and what's inside the prompt.

Knowledge cutoffNothing after the training date. Ask about last week and it guesses.
HallucinationWhen it doesn't know, it may fill the gap confidently. A better prompt just makes the guess sound better.
Missing contextYour private data, niche rules and customer history aren't in the model.
No enforcement"Never delete production data" is guidance. Nothing stops the call if Claude misreads a situation.

Fix for knowledge gaps: grounding

Give the model real, current data at the moment it needs it: RAG, tool use, structured data pipelines.

Fix for rule-breaking: enforcement

Put hard rules in code that runs before execution: programmatic gates and hooks.

Prompt engineering is a skill; correctness is an architecture. On the exam, when a rule must always hold (money, deletes, compliance), choose the programmatic control over "add it to the system prompt".

What is a programmatic gate?

Logic you write that sits between Claude's decision and the real action. It looks at the tool name and parameters, applies your rules, and either lets the call run, blocks it, or modifies it. It's code, not a human reviewing every step, and it runs before the tool does.

Why not just remove risky tools? Because one tool often does safe and unsafe things. A database tool reads and writes. A file tool touches public and sensitive folders. Some rules live outside Claude's view entirely: approvals, rate limits, allowed hours. A gate enforces all of these at the system level, so Claude can reason freely without being overly cautious.

import json, re

# Words that turn a read into a write or a destructive change
BLOCKED_SQL = {"DROP", "DELETE", "TRUNCATE", "ALTER", "UPDATE", "INSERT", "GRANT", "REVOKE"}

def gate(block) -> tuple[bool, str]:
    """Return (allowed, reason). Runs BEFORE the tool executes."""
    if block.name == "run_sql":
        words = set(re.findall(r"[A-Za-z_]+", block.input.get("query", "")))

            return False, "Blocked: changing credit_limit or email needs an approved ticket_id."
    return True, ""

            "hookEventName": "PreToolUse",

        }}

async def audit(input_data, tool_use_id, context):
    with open("audit.jsonl", "a") as f:
        f.write(json.dumps({
            "time": datetime.now(timezone.utc).isoformat(),
            "tool": input_data["tool_name"],
            "input": input_data["tool_input"],
        }) + "\n")
    return {}

# --- PostToolUse: mask secrets before Claude reads them ---
async def mask_secrets(input_data, tool_use_id, context):
    text = json.dumps(input_data.get("tool_response", ""))
    if SECRET.search(text):
        return {"hookSpecificOutput": {
            "hookEventName": "PostToolUse",
            "updatedToolOutput": SECRET.sub("[REDACTED]", text),
        }}
    return {}

    allowed_tools=["Read", "Bash"],

Tool Descriptions

When Claude has several tools, it reads their descriptions to decide which one fits the request. A vague description makes Claude guess. A precise one makes the right choice obvious.

60-second summary
  • Tool descriptions are the primary mechanism Claude uses to select a tool.
  • Wrong tool picked? Fix the description first: lowest effort, fixes the root cause. Few-shot examples, routing classifiers and merging tools come later, if at all.
  • Five elements: what it does · inputs · example uses · edge cases · boundaries.
  • Similar tools need "do not use for X, use Y instead" clauses pointing at each other.
  • A tool that does too many things should be split. Clear names help too.
  • After changing descriptions, re-read the system prompt for instructions that pull toward one tool.

Why tool descriptions drive selection

A description is a plain-language label that tells Claude three things: what the tool is, what it does, and what it doesn't handle. On every request, Claude reads all the descriptions, compares them with the request, picks the best match and calls it.

  1. User sends: "Check my order ORD-12345."
  2. Claude reads every tool description at once.
  3. It matches the request to the best description.
  4. It calls that tool with the arguments it extracted.

With vague descriptions

Claude calls get_customer instead of lookup_order. The user sees their profile instead of their order, any later steps in the workflow break, and the product looks broken.

The rule

When Claude routes to the wrong tool, fix the description first. Not the routing logic, not the architecture, not the examples.

What vague descriptions look like

These look fine to a human, but both start with "Retrieves" and both are about something a customer cares about. For "What's the status of order 12345?", either could plausibly apply.

Specificity beats length. One well-placed sentence (inputs, or a boundary) does more than a paragraph of generic wording.

How to diagnose tool misselection

Scenario: "Check my order 12345" goes to get_customer. You're offered four fixes. Only one targets the root cause: both descriptions have the same structure and no boundaries.

B. Add few-shot examplessymptomShows the right answer without explaining why. The confusion stays, and tokens go up.

Four-step diagnosis

  1. Reproduce the exact request that triggered the wrong tool.
  2. Compare the descriptions side by side. Look for overlapping wording.
  3. Find the missing signal: what information would have pointed to the right tool?
  4. Add that signal: input formats, outputs, or a boundary clause.

Error Handling Patterns

Tools and MCP servers talk to systems that fail. Reliable tools don't avoid every failure. They work out which kind of failure happened, respond to that kind, and report it in a form Claude can reason about.

60-second summary
  • Transient (timeout, 429, 503): temporary. Retry with capped exponential backoff and jitter, then fail gracefully.
  • Validation (missing field, wrong type): the request is wrong. Don't retry; say exactly which field and what's expected.
  • Business logic (out of stock, over limit): valid request, not allowed. Don't retry; explain the rule and any alternatives.
  • Permission (authenticated but not authorized): don't retry; return a safe message, log it, escalate if needed.
  • An access failure is an error; an empty result is a success. Never return [] for both.
  • Good errors are specific, labeled by category, and clean for users (details go to logs).

Every failure question on the exam comes down to classifying the failure first, then choosing the matching response. Section 02 covered how a coordinator reacts; this section covers how a tool should detect and report each type.

How to handle transient failures

Temporary and recoverable: a slow network, a rate limit, a service briefly down, an MCP server connection that dropped. Trying again a few seconds later may work. An invalid API key won't, so that's a permanent failure.

Max retry countStop after N tries (e.g. 3–5). Never infinite.
Exponential backoffWait 1s, 2s, 4s… so an overloaded service can recover.
JitterAdd randomness so many clients don't retry at the same instant.
Log & degradeLog each failure; after the last try, return a structured error instead of hanging.
retry.py · capped exponential backoff with jitter
import logging, random, time
import requests

RETRYABLE_STATUS = {429, 500, 502, 503, 504}   # temporary
MAX_ATTEMPTS = 4
BASE_DELAY = 1.0                               # seconds
MAX_DELAY = 20.0

class TransientError(Exception): ...

def call_with_retry(url: str, **kwargs) -> dict:
    for attempt in range(1, MAX_ATTEMPTS + 1):
        try:
            resp = requests.get(url, timeout=10, **kwargs)
        except (requests.Timeout, requests.ConnectionError) as e:
            reason = f"network: {type(e).__name__}"
        else:
            if resp.status_code not in RETRYABLE_STATUS:
                resp.raise_for_status()        # 4xx like 400/401/403/404: fail fast, no retry
                return resp.json()
            reason = f"HTTP {resp.status_code}"
            if "Retry-After" in resp.headers:  # server told us how long to wait
                time.sleep(min(float(resp.headers["Retry-After"]), MAX_DELAY))
                continue

        if attempt == MAX_ATTEMPTS:
            logging.error("giving up after %d attempts: %s", attempt, reason)
            raise TransientError(f"Service unavailable after {attempt} attempts ({reason}). Try again later.")

        delay = min(BASE_DELAY * 2 ** (attempt - 1), MAX_DELAY)      # 1, 2, 4 ...
        delay = random.uniform(0, delay)                              # "full jitter"
        logging.warning("attempt %d failed (%s); retrying in %.1fs", attempt, reason, delay)
        time.sleep(delay)

The official Anthropic SDKs already retry connection errors, 408, 409, 429 and 5xx responses with backoff (2 retries by default, set with max_retries). You need your own logic for the external APIs your tools and MCP servers call.

Exam trap

Infinite retries, or retries with no delay, hammer an overloaded service and can cause cascading failures across connected systems. In an MCP chain (Claude → MCP server → database/API), the server should retry briefly itself and then return a clear structured error to Claude, not crash or hang.

How to handle validation failures

The input doesn't match what the tool expects: a missing field, a number sent as text, invalid JSON, an unsupported enum value. The same request will fail every time, so don't retry. Reject it early, before it reaches downstream systems, and tell the caller exactly how to fix it.

How to handle business logic failures

The format is right, the system is up, the call ran, and the answer is still no: a transfer exceeds available funds, an item is out of stock, a booking is over capacity, an account is suspended. Not transient (retrying won't change it unless the condition changes) and not validation (the input is fine).

A good business-failure response says what rule was violated, why the request failed, and whether recovery is possible. That lets Claude tell the user clearly and suggest a next step instead of retrying.

How to handle permission failures

Authentication: who are you?

Proving identity. Invalid or expired token → typically 401.

Authorization: what may you do?

Identity is known but the action isn't allowed. Missing scope, admin-only tool → typically 403.

A valid token doesn't mean unlimited access. In MCP, permissions can be checked in several places: the MCP server authenticates the token, checks whether it may use that tool, and the downstream API may enforce its own rules too.

Access failure vs valid empty result

Both can come back with "no data", but they mean opposite things.

The query ran fine and nothing matched: zero search hits, an empty inbox. Not an error, so no retries, no alerts.

How to design distinguishable error responses

Errors usually go wrong in one of two ways: too vague to act on ("something went wrong") or a raw dump of internals. Aim between the two. In multi-step pipelines, an unclear error at step 2 can quietly derail everything after it.

Input errorThe request is the problem: missing field, ambiguous instruction, unusable format.
Tool / execution errorAn external resource failed: timeout, permission, unexpected response.
Policy refusalNot a malfunction: the request is outside what's permitted. Say so clearly without exposing the policy's internal reasoning.

Three principles

  1. Be specific. Answer "what failed?" and "what can be done?". "The search tool returned no results; try a broader query or check the data source is connected" beats "I can't do that".
  2. Categorize with labels. A field like error_type: "tool_error" lets an orchestrator decide retry, reroute or escalate without parsing free text. This matters most when Claude's output feeds another model.
  3. Contain what you reveal. No stack traces, internal endpoint or tool names, or system prompt fragments in user-facing output. Detailed and diagnostic in logs; clean and safe in outputs.

import requests

def search_customers(args: dict, token: str) -> dict:
    """Returns a Messages API tool_result body: {'content': str, 'is_error': bool}."""
    # 1. Validation: fail fast, no retry
    if not args.get("city"):
        return err("validation", "Missing required field: city", retryable=False)

    # 2. Call with retry for transient failures only

        data = call_with_retry(f"https://crm.internal/api/customers?city={args['city']}",
                               headers={"Authorization": f"Bearer {token}"})

        return err("transient", str(e), retryable=True)
    except requests.HTTPError as e:

        logging.error("CRM error %s: %s", code, e.response.text)   # details to logs only
        if code == 401:
            return err("permission", "Authentication failed: the CRM token is invalid or expired.", retryable=False)
        if code == 403:

        if code == 409:

    # 3. Success, even when empty
    return {"content": json.dumps({"customers": data, "count": len(data)}), "is_error": False}

MCP Configuration

MCP (Model Context Protocol) lets Claude discover and use external tools from what's declared in configuration. That configuration can live in more than one place, and which place you choose decides who shares it, what it can reach, and where your secrets go.

60-second summary
  • Project config = .mcp.json in the repo root. Committed, shared by the whole team, only what this project needs.
  • User config = your home directory (~/.claude.json). Your personal servers across all projects. Never committed.
  • Both are active together. On a name conflict, project beats user (and a private local entry beats both).
  • Secrets are environment variable references (${GITHUB_TOKEN}), never inline values. A committed key stays in git history.
  • Transports: stdio for local processes, HTTP for remote (SSE is the older, deprecated remote transport).
  • Server missing? Check in order: declared correctly → running → approved → env vars set.

How to diagnose missing MCP server access

A tool you configured doesn't appear, or Claude says it has no access. Work through four checks, in order.

  1. Is it declared correctly? Is the entry in the right file (.mcp.json or your user config), is the server name spelled exactly right, and is the transport right? A local process needs stdio, a remote URL needs http (or sse). A wrong transport fails silently.
  2. Is the server running or reachable? For stdio, the command must start and not crash; run it by hand to see. For remote servers, test the URL with curl. Check the server's own logs.
  3. Is it approved? Claude only connects to servers you've explicitly approved. That's a security boundary, not a bug. Run /mcp to see connected, pending and failed servers; approve pending ones.
  4. Are its environment variables set? The variable must exist in the shell where Claude Code started. echo $VAR returning nothing means the credential is missing and authentication fails. Set it and restart Claude Code; variables aren't picked up mid-session.

Tool Scoping and Agent Roles

It seems like more tools should mean more capability. Past a point, it means worse choices. Tool scoping is deciding which tools each agent gets, and which it doesn't, based on its role.

60-second summary
  • Too many tools → more wrong selections, less context left for the task, more overlap between similar tools.
  • Guideline: accuracy drops noticeably above ~20 tools; 10–20 is the effective range; simple single-job agents may need only 3–5.
  • Over 20? Don't add more: split the work across focused agents.
  • Four questions: core job in one sentence? truly required vs convenient? duplicates? belongs to another agent?
  • Scoping gives reliability, security (least privilege, smaller blast radius) and maintainability (clear ownership).
  • Write the scope down and enforce it in config, so it's a guarantee, not a habit.

Why too many tools hurt selection

To pick a tool, Claude reasons across the names, descriptions and parameter schemas of everything it's been given. With 5 tools that's an easy decision; with 50 it becomes a search problem.

Selection errorsMore candidates and more ambiguity → Claude picks something close when the right tool exists but is hard to tell apart.
Context costEvery definition uses context window. Less room is left for history, documents and instructions, so reasoning suffers everywhere.
Semantic overlapSimilar names and descriptions build up as tools get added over time; Claude may default to the first or most familiar one.

Current platforms also help with large tool sets: Anthropic's API offers a tool search feature that loads tool definitions only when needed, and Claude Code can search MCP tools on demand. The design principle for the exam stays the same: keep each agent's tool set focused.

How many tools each agent should have

There's no single number. Give the agent exactly what its job needs, and nothing beyond that.

Lean · ~5 tools focused

Fast, accurate selection. Right for a single well-defined job.

Balanced · ~15 tools effective

Broad enough for a real workflow, still manageable.

Bloated · ~40 tools degraded

Even if each tool is well designed, the combination overwhelms reliable selection.

Four questions for sizing

  1. What is this agent's core job? If you can't say it in one sentence, the scope isn't clear yet.
  2. Which tools are genuinely required? Required means the task is impossible without it. "Convenient" isn't enough reason to add a tool.
  3. Do any tools duplicate each other? Two overlapping tools don't double the power; they double the ambiguity.
  4. Does any tool belong to another part of the system? Tools for a different workflow phase go to the agent that owns that phase.

Right-sizing, not minimalism: the minimum tool set that makes the agent fully capable of its role. An agent growing past 20 tools is a design signal to redesign, not a reason to keep adding.

How to scope tools to agent roles

Both halves matter: which tools an agent gets, and which it deliberately doesn't. The result should be a clean mapping where every tool is there because of the agent's job.

ReliabilityFocused sets mean fewer selection errors and more consistent behavior.
SecurityLeast privilege. If the code agent misbehaves, it can't touch email or calendar. Scope limits the blast radius.
MaintainabilityClear ownership: when something breaks, you know which agent and which tools to look at.
AgentJobHasDeliberately doesn't have
ResearchFind and synthesize informationWeb search, document reading, summarizationCode execution, email
CodeWork with codeExecute, read file, write file, lintEmail, calendar, web search
OpsCommunication and task workflowsEmail, calendar, task creationCode execution, document retrieval

A repeatable scoping process

  1. Write the agent's job in one sentence. Everything else is checked against it.
  2. List the tools that are truly required. If the job is possible without a tool, leave it off.
  3. Remove tools another agent already owns. Duplicate access makes it unclear which agent should act.
  4. Document the scope. It becomes the design contract for your team and future maintainers.
check_scopes.py · catch bloated or overlapping agents before they ship
from collections import defaultdict

AGENTS = {
    "research": {"job": "Find and synthesize information from the web and documents.",
                 "tools": ["web_search", "read_document", "summarize"]},
    "code":     {"job": "Write, run and lint code in the repo.",
                 "tools": ["run_code", "read_file", "write_file", "lint"]},
    "ops":      {"job": "Handle email, calendar and task follow-ups.",
                 "tools": ["send_email", "create_event", "create_task"]},
}
MAX_TOOLS = 20

def check(agents: dict) -> list[str]:
    problems, owners = [], defaultdict(list)
    for name, spec in agents.items():
        if len(spec["tools"]) > MAX_TOOLS:
            problems.append(f"{name}: {len(spec['tools'])} tools; split this agent")
        if not spec.get("job") or spec["job"].count(".") > 1:
            problems.append(f"{name}: job should be one clear sentence")
        for tool in spec["tools"]:
            owners[tool].append(name)
    for tool, names in owners.items():
        if len(names) > 1:
            problems.append(f"'{tool}' is owned by {names}; give it to one agent")
    return problems

print(check(AGENTS) or "All scopes OK")

CLAUDE.md Hierarchy

CLAUDE.md files are plain markdown instructions that Claude Code loads automatically. Instead of one big file, they live at several levels: the whole repository, single folders, and your own machine. Where you put a rule decides who gets it and when.

60-second summary
  • Project ./CLAUDE.md (or ./.claude/CLAUDE.md): repo-wide standards, committed, shared by the team, loaded every session.
  • Directory frontend/CLAUDE.md: rules for one folder only, loaded when Claude works with files there.
  • User ~/.claude/CLAUDE.md: your personal preferences in every project, never shared.
  • "Chat is for this session; CLAUDE.md is for every session." Keep it specific, stable and under ~200 lines.
  • CLAUDE.md is context, not enforcement. For a rule that must always hold, use a hook (section 04).
  • Conventions ignored for one developer? Check: shared? committed? right scope? onboarding consistent?

What goes in project-level CLAUDE.md

Belongs here

Build and test commands · repo structure · coding standards · naming conventions · architecture patterns · documentation expectations · shared workflows.

Doesn't belong here

One-off debugging instructions · temporary experiments · session-specific tasks · vague advice ("write good code") · large pasted documentation · personal preferences.

What goes in user-level CLAUDE.md

Lives in ~/.claude/CLAUDE.md on your machine. It applies to all your projects and is never shared through git.

Personal: belongs here

"Keep explanations concise" · "I use pnpm, not npm" · "Prefer TypeScript examples" · editor and terminal habits · personal shortcuts.

Team: never only here

Coding standards · repo workflows · naming conventions · architecture rules · testing requirements. Teammates and new hires won't get them.

The rule: affects only your workflow → user-level. Affects the project or the team → project-level CLAUDE.md, committed.

How the files load and combine

  1. At launch, Claude Code loads your user file and every CLAUDE.md in the folder you started in and each folder above it.
  2. On demand, a CLAUDE.md in a subfolder loads the first time Claude reads, writes or edits a file in that subfolder.
  3. They combine: all loaded files are added to context together. Broader files come first, more specific ones later.

Exam trap

CLAUDE.md is guidance, delivered as context. Claude tries to follow it, but it's not guaranteed. For "must never happen" or "must run before every commit", use a hook or permission rule (section 04).

How to diagnose ignored team conventions

Same repo, but one developer's Claude follows the standards and another's doesn't. It's almost always a configuration-scope problem, not a model problem: local configuration produces local behavior.

  3. Is there a scope mismatch? Team standards at user level, or personal habits in the project file.
  4. Does onboarding give everyone the same behavior? "If a new developer clones the repo today, will Claude follow our conventions?" If not, the shared setup is incomplete.

Path-Specific Rules and context: fork

Both features keep Claude's context focused. Path-specific rules load instructions only when Claude touches matching files. context: fork runs a skill's heavy exploration in a separate subagent and brings back only the findings.

60-second summary
  • Path-specific rules: markdown files in .claude/rules/ with YAML paths: globs. They load only when Claude reads or edits a matching file.
  • Deciding question: where do the target files live? One folder → directory CLAUDE.md. Spread across the codebase (tests next to source) → path-specific rule.
  • Rules without paths load at launch like CLAUDE.md. Rules with paths cost no tokens until a matching file is touched, and fewer competing instructions are followed more reliably.
  • context: fork in a skill's frontmatter runs it in an isolated subagent. It gets the skill content as its prompt, no conversation history, and only a summary comes back.
  • Explore = read-only analysis · Plan = structured planning · general-purpose (default) = can change code and run commands.
  • Don't fork small skills, or skills that need earlier conversation context.

Path-specific rules

Not every instruction should apply everywhere. A path-specific rule is a markdown file in .claude/rules/ whose frontmatter says which files it's for. It activates whenever Claude works with a matching file, wherever that file sits in the project.

.claude/rules/testing.md
---
paths:
  - "**/*.test.{ts,tsx}"
  - "**/__tests__/**"
---

# Testing conventions

- Use Vitest and Testing Library; no Enzyme
- One `describe` per component or function; test names start with "should"
- Mock network calls with MSW, never with real endpoints
- Each test file must clean up timers with `vi.useRealTimers()` in `afterEach`
Glob patternMatches
**/*.tsEvery TypeScript file, any folder
src/**/*Everything under src/
*.mdMarkdown files in the project root only
src/components/*.tsxComponents in that one folder
src/**/*.{ts,tsx}Brace expansion: .ts and .tsx under src/

Quote each glob in the YAML. An unquoted value starting with * is read as a YAML alias and breaks the frontmatter. A rule file without paths applies to all files and loads at launch.

Path-specific rules vs directory CLAUDE.md

Both scope instructions to part of the codebase. The exam asks you to choose between them, and the deciding factor is where the target files actually live.

Directory CLAUDE.md

Bound to one location. Loads when Claude works with files in that folder. Right when conventions are neatly contained: mobile/, infra/, a single tests/ folder.

Path-specific rule

Bound to a file pattern. Loads when Claude works with any matching file. Right when files are spread out: all *.test.tsx files, all API handlers, all migrations.

The introduction video says directory-level CLAUDE.md files "load when Claude Code starts". They don't: a subdirectory's CLAUDE.md loads when Claude first reads, writes or edits a file in that folder (section 09). The next video states it correctly.

How path-specific rules affect the token budget

Every line in context costs tokens on every message. A CLAUDE.md past 300 lines that loads your Terraform checklist while you fix one CSS file is spending tokens on nothing, and Claude follows it less reliably.

CLI Flags and CI/CD

Claude Code is interactive by default: it expects a person at the terminal. In a CI pipeline there's no one there, so the job hangs. These flags make Claude Code take a prompt, print the result and exit.

60-second summary
  • -p (print) runs Claude Code non-interactively: process the prompt, write to stdout, exit. A hanging CI job → the answer is -p.
  • --output-format json gives machine-parsable output; add --json-schema to force a structure (it arrives in structured_output).
  • Pipe content in (git diff | claude -p "…"), resume sessions (--resume), and pre-approve tools (--allowedTools).
  • CI recipe: non-interactive + structured output, project context via CLAUDE.md, separate sessions for writing vs reviewing.
  • A session that wrote the code carries its own reasoning and is less likely to question it. An independent reviewer catches more.

What the -p flag does

Without -p

claude "Analyze this PR for security issues" opens an interactive session and waits for input that never comes. The CI job hangs until it times out.

With -p

claude -p "Analyze this PR for security issues" processes the prompt, prints the result to stdout and exits. No human in the loop.

basic non-interactive use
# One question, answer on stdout
claude -p "What does the auth module do?"

# Pipe content in, redirect the answer out
cat build-error.txt | claude -p "Concisely explain the root cause of this build error" > output.txt

# Use it as a step in a script: branch on the exit status
if claude -p "Do the tests in tests/ cover the refund flow? Answer YES or NO only." | grep -q YES; then
  echo "coverage ok"
fi

-p is short for --print. The process exits 0 on success and non-zero when the run fails. Piped input is capped at 10 MB; for bigger inputs, write a file and reference its path.

Match Criteria and Few-Shot Examples

A code reviewer that floods developers with false positives soon gets ignored. The problem usually isn't Claude's ability but a vague prompt. This section is about turning "be careful" into rules Claude can apply the same way every time.

60-second summary
  • "Only report if you're confident" / "be conservative" don't improve precision: Claude has no confidence dial you can tune with an adjective.
  • Use explicit match criteria: category, what qualifies, what doesn't, plus a concrete example and severity definitions.
  • Define non-matches too: acceptable patterns, scope exclusions, and how to handle ambiguous input (e.g. an unclear enum, nullable fields).
  • False positives in one category erode trust in all categories. Fix the criteria, or temporarily disable noisy categories.
  • Few-shot comes after explicit instructions, when output is still inconsistent. Use 2–4 targeted examples, each covering a different failure mode.
  • Examples must show the reasoning, not just input → output, so Claude generalizes the judgment to new cases.

Why "only if you're confident" doesn't work

Confidence-based filtering

"Only report real issues." "Be conservative." "Only flag things you're sure about." These give Claude nothing concrete to test against, so it applies its own judgment, differently each time.

Categorical decisions

"Report: bugs, security vulnerabilities, data races, logic errors. Skip: style, local naming, subjective preferences." Each finding either meets a stated test or doesn't.

The downstream cost: high false positives in one category undermine trust in every category. Once developers learn to ignore half the findings as noise, they ignore the real bugs too.

The two strategies from the exam guide

  1. Write specific review criteria that say which issues to report (bugs, security) and which to skip (minor style, local patterns).
  2. Temporarily disable high-false-positive categories to restore trust while you improve the prompt for those categories.

How to write explicit match criteria

Each criterion has three parts: the category, what qualifies, and what doesn't qualify. Without the third part, Claude over-matches.

Vague

"Check that comments are accurate."

Explicit

"Flag a comment only when the behavior it claims directly contradicts what the code does." This implies what to skip: comments that are merely incomplete or describe intent.

review_prompt.py · categories, examples, skips, severity
REVIEW_SYSTEM = """You review pull request diffs. Report ONLY findings that match a category below.

<report_categories>
1. Bug: code that produces a wrong result or crashes for a valid input.
   Example: `for i in range(len(items) + 1): total += items[i]` raises IndexError on the last pass.
2. Security vulnerability: untrusted input reaches a sensitive sink without validation.
   Example: `cursor.execute(f"SELECT * FROM users WHERE id = {request.args['id']}")` (SQL injection).
3. Data race: shared mutable state accessed from concurrent code without a lock.
   Example: two worker threads both run `counter += 1` on a module-level int.
4. Logic error: a condition or calculation that contradicts the stated requirement.
   Example: discount applied when `total < 100` but the ticket says "orders over 100".
5. Inaccurate comment: the behavior a comment claims directly contradicts the code.
   Example: `# returns None if not found` above a function that raises KeyError.
</report_categories>

<do_not_report>
- Minor style or formatting (Prettier/Black handle it).
- Local naming choices: `data` vs `response_data`, `tmp` for a loop temporary.
- Subjective preferences ("I'd use a dict comprehension here").
- Comments that are incomplete or describe intent rather than claim behavior.
</do_not_report>

<severity>
- critical: data loss or an exploitable security hole. Example: SQL injection above.
- high: wrong results for common inputs. Example: off-by-one in the totals loop.
- medium: wrong results only under specific conditions. Example: timezone bug at midnight UTC.
- low: inaccurate comment or a hard-to-trigger edge case.
</severity>

If nothing matches a category, return an empty findings list. Do not invent findings."""

The example per category is critical: it anchors the definition so Claude can't stretch a category to fit borderline cases. This structure (definition + example + severity) is what the exam means by "explicit criteria".

Defining non-matches and edge cases

If you only describe what to flag, Claude has to guess about everything else, and it tends to over-flag, because reporting something feels safer than missing it. A variable named temp in a loop gets flagged as a naming violation.

1. Acceptable patternsLook like issues but are intentional: high complexity in a well-structured state-machine handler, a deliberate except: pass in a cleanup hook.
2. Scope exclusionsWhole categories you won't review: style, local naming, subjective formatting. Listing them stops Claude inventing findings there.
3. Edge-case handlingWhat to do when input fits neither side. In schemas: an unclear enum value, or nullable fields.
schema that gives Claude an honest way out (links to task 4.3)
{
  "type": "object",
  "properties": {
    "category":  { "type": "string", "enum": ["bug", "security", "data_race", "logic", "comment", "unclear"] },
    "severity":  { "type": "string", "enum": ["critical", "high", "medium", "low"] },
    "line":      { "type": "integer" },
    "explanation": { "type": "string" },
    "ticket_ref": { "type": ["string", "null"], "description": "Only if the diff or PR text names a ticket; otherwise null" }
  },
  "required": ["category", "severity", "line", "explanation"]
}
Exam point

If a field is required but the source document may not contain that information, Claude may fabricate a value to fill it. Make such fields optional or nullable, and give ambiguous cases an explicit value like unclear.

When to reach for few-shot examples

The exam guide calls few-shot examples the most effective technique for consistent, actionable output when detailed instructions alone still produce inconsistent results. They're not the first resort.

SignalExample
Inconsistent format despite clear instructionsOne run returns bullets with severity labels, the next a paragraph of prose
Inconsistent handling of ambiguous casesA borderline request goes to a different tool on each run
Empty/null extraction of fields that are present in varied formatsSources given as inline citations in one document and a bibliography in another; the extractor misses one style

Examples teach judgment, not just format. Good examples let Claude generalize to new patterns rather than only matching the cases you listed. They're also the exam's answer to null or hallucinated extraction from documents with varied layouts.

How many few-shot examples to include

The number: 2–4 targeted examples

At least two so Claude can extract a pattern. Not many more, because every example costs context tokens in production.

"Targeted" means…

Each example shows how to handle a different type of ambiguity, edge case or format variation that instructions alone couldn't resolve.

  1. Find the 2–4 ambiguity types that cause the most inconsistency in your output.
  2. Write one example for each. Not three examples of the same case.
  3. Prefer edge cases over standard cases. Your explicit criteria already handle the standard ones.
  4. Include the reasoning for why one action was chosen over plausible alternatives.

Scenarios the exam guide lists for examples: tool selection for ambiguous requests, branch-level test coverage gaps, informal measurements ("a couple of cups", "about a mile"), and varied document structures (inline citations vs bibliographies).

Why examples must show reasoning, not just answers

Input → output shows Claude what to do. Input → reasoning → output teaches it how to decide. Without reasoning, surface features (specific words, numbers, phrasing) get too much weight.

Answer only

Input: "I bought this jacket for $89 last week and want to return it."
Output: {"refund_amount": null}

What did it learn? Skip when "bought" appears? When the amount is under $100? When clothing is mentioned? It can't tell.

Reasoning included

Input: same email.
Reasoning: "$89 is the original purchase price, not a stated refund amount. They want a return, but no refund amount was requested or agreed."
Output: {"refund_amount": null}

JSON Schema and Structured Output

Asking Claude to "return JSON" works most of the time. At production volume, "most of the time" means broken records every day. This section covers getting output that always parses, then the harder problem: output that parses perfectly and is still wrong.

60-second summary
  • Don't ask for JSON as free text. Define a tool with an input schema and let Claude answer with a tool_use block: no code fences, trailing commas or broken brackets.
  • The schema guarantees structure, not truth. Line items can still not add up; values can still be invented.
  • Fabrication is silent: it parses, validates, raises no alert, and spreads into databases, payments and emails.
  • A required field that the source doesn't contain forces Claude to invent a value. It's the schema's fault, not the model's.
  • Toolkit: no value → optional or nullable (nullable is the safer default); ambiguous → unclear; unexpected → other + detail.
  • Retry with error feedback = original task + previous output + specific error, capped at 2–3 tries, and only for errors the source can fix.

How tool_use with a JSON schema prevents syntax errors

Free-text JSON

"Extract the line items and return as JSON." Sometimes you get ```json fences, a trailing comma, a stray comment, or a missing bracket from a cut-off response. Teams pile on fence-strippers, regex fixes, repair libraries and retries, and it still breaks every few hundred requests.

tool_use with a schema

Define a tool like record_invoice with an input_schema. Claude responds with a tool_use block whose input is already a structured object. No parsing or clean-up step.

Fix it at the source, not downstream. Every patch after the model is a workaround for treating it like it's typing JSON into a text box. The exam treats tool_use + JSON schema as the standard answer for schema-compliant output.

Current API detail

The course says the API validates the tool input against your schema. That's guaranteed only with strict mode: "strict": true on the tool (which also requires "additionalProperties": false on every object), or the separate JSON outputs feature (output_config.format). Without strict, Claude follows simple schemas very reliably but it isn't enforced. Forcing the tool with tool_choice works on older models; the newest Opus/Sonnet 5.5 reject forced tool_choice, so ask for the tool in the prompt as above (section 05).

Why schemas don't prevent fabricated data

The schema says invoice_number is required. The document is a receipt with no invoice number. Claude returns "INV-2024-001" anyway. It parses, it validates, it gets stored.

Syntax errors are loud

The parser throws, the pipeline alerts, a human looks. Bad data never reaches production.

Fabrication is silent

No exception, no alert. The fake value looks exactly like a real one, so you find out only when a customer disputes a charge or an audit fails.

Two common mistakes

1. Treating tool_use as a complete solution: "it validated, so it's correct". 2. Making every field required "so we always get it", which just means you always get it, sometimes invented.

The model isn't hallucinating; it's following your contract. The fix isn't a smarter model or a stricter prompt. It's better schema design.

Why required fields cause empty-field fabrication

"Required" doesn't mean "I want this field". It means "an output without this field is forbidden". When the value isn't in the source, Claude has two paths: leave it out (output invalid, rejected) or produce something (output valid, accepted). It takes the second path every time, because the schema gives it no way to say "not in the source".

How to use optional and nullable fields

Optional

Remove the field from required. Present in source → key appears; absent → key is missing. Downstream code must handle a missing key (result.get("invoice_number"), not result["invoice_number"]).

Nullable safer default

Keep it in required, set "type": ["string", "null"]. The key is always there; the value may be null. Same shape every time, good for databases, UIs and typed code.

before → after: fix only the fields that are often absent

Using enum values for ambiguity

Optional and nullable fields handle a missing value. Two cases remain where the value is present but doesn't fit, and Claude would otherwise pick the closest-looking option.

Ambiguous → "unclear"

"My package never arrived and I was charged twice." Shipping or billing? Without unclear, Claude picks one and the uncertainty vanishes. With it, the ticket can go to a human.

Unexpected → "other" + detail

A fitness tracker in an enum of electronics/clothing/home/food might get labeled "home goods". Instead: category: "other", category_detail: "fitness tracker", which shows you how to improve the enum later.

Retry with error feedback

The JSON is well-formed, every field is present, every type is correct, and the line items (400 + 250 = 650) don't match the stated total of 750. A bare "try again" makes Claude guess what was wrong and often repeat the same blind spot.

validated_extract.py · semantic checks + targeted retries
import json

MAX_ATTEMPTS = 3

def semantic_errors(data: dict) -> list[str]:
    errors = []
    items_sum = round(sum(i["amount"] for i in data["line_items"]), 2)
    if abs(items_sum - data["total"]) > 0.01:
        errors.append(f"total is {data['total']} but line_items sum to {items_sum}. "
                      "Recheck the total and each line item against the document.")
    if data["total"] < 0:
        errors.append(f"total is negative ({data['total']}).")
    return errors

def extract_with_feedback(document_text: str) -> dict:
    messages = [{"role": "user", "content":
        "Use the record_invoice tool to record this document. "
        "Use null for fields the document does not contain.\n\n" + document_text}]

    for attempt in range(1, MAX_ATTEMPTS + 1):
        resp = client.messages.create(model="claude-sonnet-5-5", max_tokens=2048,
                                      tools=[RECORD_INVOICE], messages=messages)
        call = next(b for b in resp.content if b.type == "tool_use")
        errors = semantic_errors(call.input)
        if not errors:
            return call.input

        # Feed back: previous output (assistant turn) + the specific error (tool_result)
        messages.append({"role": "assistant", "content": resp.content})
        messages.append({"role": "user", "content": [{
            "type": "tool_result", "tool_use_id": call.id, "is_error": True,
            "content": "Validation failed:\n- " + "\n- ".join(errors) +
                       "\nCall record_invoice again with corrected values from the document.",
        }]})

    raise ValueError(f"Still invalid after {MAX_ATTEMPTS} attempts: {errors}")  # surface, don't loop

Fixable: retry helps

A misread number, a value in the wrong field, a transposed digit. The right answer exists in the source, so Claude can find it again.

Unfixable: retry hurts

The information was never in the document. Retrying can't extract it, and pushing harder risks a plausible-looking invented value. Return null or send it to a human instead.

Before building a retry loop, ask: can Claude recheck this against the source, or is the source itself incomplete? Cap retries at 2–3, then surface an error.

API Selection and Cost vs Latency

The wrong API pattern either doubles your bill or breaks the user experience. Pick the API from the workload's latency needs first, then make it cheaper with model choice, caching and thinking settings.

60-second summary
  • Sync = blocking request; use it when a user, workflow or downstream system is waiting (chat, pre-merge review, agent loops, fraud checks).
  • Batch = submit → wait (up to 24 h) → retrieve, at 50% of the price. For overnight reports, audits, bulk enrichment, nightly test generation.
  • Batch limits: no live multi-turn tool loop inside a request; match results by custom_id.
  • SLA rule: submission interval + 24 h ≤ SLA. Always reason about the worst case.
  • Latency is the constraint, cost is the variable. Decide per workload; most mature products run sync and batch side by side.
  • Then optimize cost: right model (Opus/Sonnet/Haiku), prompt caching for large repeated context, extended thinking only for hard problems.

When to use the synchronous API

A synchronous call is a blocking request: your app sends it, waits with the connection open while Claude generates, and continues once the response arrives. Same as any other API call.

The one question: is something actively waiting on this response? It's not about volume, overall cost or raw latency alone. It's whether the response is on the critical path of something else.

Live user interactionChat, search assistants, autocomplete, copilots.
Pre-merge code reviewCI check that must pass before the PR can merge.
Agent workflowsEach step's output decides the next tool call.
Real-time decisionsFraud checks, ticket routing, moderation before publishing.
The common mistake

A team sees "50% off" and moves everything to batch. The live chat that replied in 3 seconds now replies 20 minutes later; pre-merge reviews take hours; agent workflows break. Batch saves money by trading away latency, which waiting workloads can't afford.

When to use the Batch API

Overnight reportingDaily summaries, briefings, digests ready by morning.
Periodic auditsCompliance reviews, moderation of archives, security scans.
Bulk enrichmentClassify, tag, summarize or extract across large collections.
Nightly test generationSynthetic tests ready before the morning CI runs.

The pattern: there's still a deadline, but it's hours away, not seconds. Input, output and cached tokens are all billed at half price, with the same models and prompts.

Two constraints to design around

No live multi-turn tool loop

Each batch request is processed as one isolated call. A workflow where one response decides the next prompt or tool call (an agent loop) can't run inside a batch. Keep agent loops synchronous.

Request correlation

Give every request a custom_id. Results can come back in any order, and the ID is the only reliable way to match an output to its input. Plan your ID scheme before the first submission.

How to choose between cost and latency

"Balance cost and latency" is the wrong framing; they aren't equals. Latency is set by the workload: a live chat needs seconds, a daily report needs "before morning". Those are constraints, not preferences. Cost is flexible and can be tuned in many ways inside whichever API you've chosen.

The real question: given my latency constraint, what's the cheapest way to meet it?

The hybrid pattern is normal

Same codebase, same model family: sync for live customer chat, batch for overnight analytics behind the next morning's dashboards. Forcing everything through one API means either the product is very early or one workload is on the wrong API.

Then optimize cost

Smaller models for simple tasks, prompt caching for repeated context, tighter prompts. Batch workloads get all of these plus the 50% starting discount. None of these change the API choice.

Two mistakes

1. Treating cost and latency as symmetric, which is how live chat ends up on batch to save a few cents. 2. Asking "sync or batch?" once for the whole product. Ask it per workload.

Extended thinking

Some questions need more reasoning, not better wording. With thinking on, Claude works through the problem step by step (checking its logic, reconsidering assumptions) before writing the answer.

Use it for depth

Complex math and proofs, tricky coding problems, high-stakes trade-offs, dense document analysis, structured scientific reasoning. "Would you want a smart person to sit and think first?"

Skip it for speed

Straightforward or factual questions, mostly creative tasks, chat that must feel instant, live search, autocomplete, high volumes of simple calls. It adds latency and cost without adding value.

Context Window Management

A well-built system can still fall apart in long conversations or huge prompts. That's usually a context management problem, not a model problem. This section covers keeping what matters exact, placing it where Claude reads it best, and keeping the noise out.

60-second summary
  • Progressive summarization compresses older turns to save space, and quietly rounds amounts, percentages and dates ($89.99 → "about $90").
  • A case-facts block keeps identifiers, exact dates/amounts, the request, and status outside the conversation and sends it word-for-word every turn.
  • Lost in the middle: recall is strongest at the start and end of a long context and weakest in the middle (a U-curve).
  • Put long documents at the top, the question and instructions at the bottom (up to 30% better answers in Anthropic's tests). Ask for relevant quotes first.
  • XML tags (<instructions>, <examples>, <document>…) separate rules from examples from data.
  • Trim tool results: filter at the source, post-process before injecting, or summarize. Claude should see only what it needs.

Domain 5 at a glance

One core idea: keep the system reliable as context grows, tasks get messy and things go wrong.

1. Context qualitySummarization loss, key facts placement, case-facts blocks, structured tags, trimming tool results. This section.
2. Human escalationValid triggers: direct request, authority gap, verification flag. Not valid on their own: frustration, complexity.
3. Multi-agent errorsStructured error context, offering alternatives, not waiting until retries are exhausted, not marking empty results as success.

How progressive summarization loses detail

Every model has a fixed context window. When a long conversation fills it, older turns get compressed into shorter, more general versions. It happens gradually: each time the conversation grows, older history is summarized again, and details fade a little each time.

Numbers$89.99 → "about $90"; a precise count → "a few".
Percentages42% → "roughly 40%"; 23% → "around a quarter".
DatesJanuary 15, 2025 → "last month"; a timestamp → "earlier today".

Original turn

"On January 15, 2025 the customer placed an order for $89.99, paid with a Visa ending 4242, requesting two-day shipping."

After summarization

"In mid-January, the customer placed a small order with expedited shipping."

Feels accurate. The date, amount and payment method are gone.

Why it's dangerous

It doesn't fail loudly. The conversation flows, Claude sounds confident, and the precision your system depends on erodes until it shows up as a wrong refund, a wrong compliance date or a wrong ID.

The compression is done by whatever manages the conversation: your application, or a tool like Claude Code when it auto-compacts a long session. It isn't the model deciding to forget mid-reply. Either way, the fix is the same: keep critical facts somewhere summarization can't touch.

What is a case-facts block?

A short list of critical details kept separate from the conversation and sent fresh, word for word, on every call. The conversation may be compressed; the block never is. Think of a sticky note on the monitor during a long phone call.

IdentifiersCustomer ID, order ID, ticket number.
Dates & amountsOrder date, refund amount, transaction time, exact values.
Issue & requestWhat the user actually asked for, stated factually.
Status & decisionsOpen or escalated? What has been promised?

The "lost in the middle" problem

How to trim verbose tool results

Tool results go straight into the context. APIs return whole objects when you need one field; searches return 10 results when you need 2; queries come back with metadata, pagination and status codes.

Fills the windowEvery token in a result is space taken from history, instructions and reasoning.
Buries the answerThe two fields you need hide among dozens; more chance of reasoning errors.
Slows and costsMore tokens on every step, multiplied across a pipeline.

Raw API response (~600 tokens)

{"status":200,"request_id":"…","timestamp":"…","region":"ap-south-1","data":{"user":{"id":…,"name":"Priya Raman","email":"priya@example.com","prefs":{…40 keys…},"audit":[…],"created_at":…}},"pagination":{…}}

What Claude needs (~20 tokens)

{"name":"Priya Raman","email":"priya@example.com"}

Same answer, roughly 95% fewer tokens.

  1. Filter at the source. Use the API's fields/select parameters; in SQL, name columns instead of SELECT * and add LIMIT.

  3. Summarize or truncate. For inherently long output (search pages, logs, big documents), pass key points or the relevant chunk; Claude can ask for more in a follow-up.

Escalation Triggers

Escalation means the agent stops and hands control to a human. Escalate too often and the agent is pointless; too rarely and it makes decisions it has no authority to make. This section is about drawing that line on purpose.

60-second summary
  • Direct human request: always valid. Honor it immediately, with no investigation first, even if the bot could solve it.
  • Authority gap: policy is silent or ambiguous on the request (competitor price match when policy covers only your own prices). The agent can't invent policy.
  • No meaningful progress (exam guide) / verification flag (course): a real signal such as a failure, denial or contradiction that the agent can't resolve.
  • Not triggers on their own: frustration, complexity, sentiment scores, self-reported confidence.
  • Frustrated + simple + in policy → acknowledge, then resolve. Escalate if they ask for a human.
  • Fix calibration with explicit escalation criteria plus few-shot examples in the system prompt, not a sentiment detector or confidence threshold.

The triggers at a glance

Course wording vs exam guide

The course lists the three valid triggers as direct request, authority gap, verification flag. The exam guide's third trigger is inability to make meaningful progress. They overlap: a verification flag is a real signal (failure, denial, contradiction, high-risk action) that must be checked before continuing, and persistent unresolved signals are what "no meaningful progress" looks like. If an answer option says "unable to make meaningful progress", treat it as the valid third trigger.

Trigger 1: a direct human request

The user explicitly says "I want to speak to a real person", "connect me to support", "can I talk to an agent". No interpretation needed: the user has decided how they want their issue handled.

Capability doesn't override preference. The question isn't "can the bot solve this?" but "did the user ask for a human?". Even if the bot could resolve the billing dispute, you hand off.

  1. Detect the intent, not the keywords. "Get me a human", "real person", "I want an agent" are all the same intent.
  2. Acknowledge immediately. "Got it, connecting you to a team member now." The user shouldn't have to repeat themselves.
  3. Don't re-prompt. The automated flow ends: no "one more question", no extra options. Complete the handoff.

Qualifying to route

"I'll connect you now. Is this about billing or an order, so I reach the right team?" asked once, alongside the handoff. Fine.

Qualifying to deflect

"Before I connect you, can you describe the issue? Have you tried our FAQ? Let me try one more fix…" A gate meant to keep the user in the bot. A trust violation users notice.

Trigger 2: an authority gap

Not about what the agent can do technically, but what it's permitted to do under its policy. An authority gap is when policy is ambiguous or silent on the specific request.

The exam's example

A customer asks for competitor price matching. Policy covers price adjustments for the company's own website only. There's no rule saying yes and none saying no, so the agent escalates.

Complex but in policy

A multi-item damage claim with photos, a partial refund and a replacement. Hard, but fully covered by policy, so the agent resolves it.

Policy gaps, not complex cases. A case can be difficult and still sit squarely inside the agent's boundaries. Difficulty isn't the question; coverage is.

Related exam nuance

A lookup returns multiple matching customers. Don't pick one using a heuristic (most recent, closest name). Ask for an additional identifier (email, order number). Guessing could take action on the wrong account.

Verification flags (course term)

In an agentic loop (gather context → act → verify), each tool result informs the next step. A verification flag is a real signal that the next step depends on checking something first. It doesn't mean the task failed.

Why frustration alone is not a valid trigger

Frustration tells you someone is unhappy, not why. The reason matters:

Wrong answerAn accuracy problem. Escalating may be right, because accuracy failed.
Repeating themselvesA context-management problem (section 16).
Slow or confusing processA UX problem. A human can't fix it faster.

  2. Restate the goal: bring the conversation back to what they're trying to get done.
  3. Check for a real trigger: explicit request? policy gap? stuck or high-risk? If yes, escalate; if not, solve it.
Careful with the course's opening example

The video opens with a customer typing "This is unacceptable. I want to speak to someone right now," and calls escalating a mistake because the answer was in the FAQ. But "I want to speak to someone" is an explicit human request, which you honor immediately (trigger 1). The lesson's point is about tone alone: all-caps anger without asking for a person is not a trigger.

Why complexity alone is not a valid trigger

Complexity describes the scope of the work; a signal means something went wrong. The agentic loop is built for complex work: evaluate, act, read the result, adjust, repeat, often 20–30 tool calls in one task. Long tasks are managed with context compaction, subagents and effort levels, not by stopping.

Complexity + signal = trigger. Complexity alone = work.

Handling a frustrated customer with a simple issue

A late package, a failed password reset, a slow refund: the customer sounds upset, but the issue is simple and within the agent's authority. Escalating on tone alone raises cost, slows resolution and overloads the human team.

Weak system

Detects anger → transfers immediately → a human spends 30 seconds pasting the FAQ answer. The customer waited longer for the same fix.

Strong system

"I'm sorry the delay has been so frustrating. I can fix this for you right now: I've reissued the label and your replacement ships today."

The exam guide's version: when the issue is within capability, acknowledge the frustration while offering resolution, and escalate if the customer still prefers a human. A clear, explicit request is honored at once; vague venting ("this is useless!") gets acknowledgement plus a real fix first.

Error Context and Common Mistakes

In a multi-agent system, a failure is only as useful as its description. This section covers reporting errors so the next layer can recover, keeping a second path ready, and getting failure information to Claude while it can still change course.

60-second summary
  • "error" alone forces the coordinator to guess, and guesses cascade into confident wrong answers.
  • Structured error context has four fields: what was attempted · what error occurred (category + retryable?) · access failure or empty result? · partial results.
  • Never throw away completed work: retry only what failed and reuse the rest.
  • Reliable systems keep alternative approaches: a backup tool or source, cached data, a simpler prompt, a clarifying question, a clear partial answer.
  • Clear errors let Claude itself pick a different path.
  • Don't hide failures behind silent retries: inform Claude after the first failure with what failed, how, and what's planned next.

Structured error context in multi-agent systems

When a subagent fails, the description it sends the coordinator decides whether the next step succeeds. A one-word error gives the coordinator nothing to act on. A structured one tells it whether to retry, reroute or escalate.

Vague

{"status": "error"}

Did the query run? Is the data missing? Should we retry? The coordinator guesses.

Structured

"Tried the query twice; the database returned an access error, so I couldn't check the records. Here are the two I retrieved before it failed."

1. What was attemptedTool called, parameters, how many retries used. Stops the coordinator repeating failed steps.
2. What error occurredThe category (transient, validation, business, permission; section 06) and whether it's retryable.
3. Access failure or empty?Did it check and find nothing, or never manage to check? Same look, opposite meaning.
4. Partial resultsWhatever finished before the failure: 3 of 5 lookups, a draft. Never discard it.

It's also a context-management win: four short, dense fields give the coordinator what it needs without re-deriving anything or reading a stack trace.

        return results

    err = report["error"]
    if report["outcome"] == "access_failure" and err["retryable"]:
        retry = retry_subagent(customers=report["not_checked"])     # only what failed
        results.update(retry.get("partial_results", {}))
        return results
    if err["category"] == "permission":
        return escalate(f"Access denied for {report['attempted']['tool']}", partial=results)
    if err["category"] == "validation":
        return escalate(f"Bad request: {err['detail']}", partial=results)
    return escalate(f"Unrecoverable: {err['detail']}", partial=results)

Why alternative approaches matter

A workflow that relies on one prompt, one tool and one retrieval strategy works until that single path fails. Reliable systems assume no method works every time and keep a second way to make progress.

Infrastructure levelA different retrieval source, a backup tool or endpoint, cached data.
Prompt levelA simpler prompt structure; relaxed formatting that still returns a useful partial answer.
Interaction levelAsk the user a clarifying question instead of guessing when context is ambiguous.

Why it compounds: in agent loops, every iteration multiplies the failure rate of the weakest step, so one brittle step early in a chain can cascade into a much larger failure. The goal isn't perfection; it's resilience.

def get_activity(customer_id: str) -> dict:
    attempts = []
    for source in (primary_api, secondary_api):
        try:
            return {"data": source(customer_id), "source": source.__name__, "attempts": attempts}
        except TimeoutError as e:
            attempts.append(f"{source.__name__}: timeout")
    cached = cache.get(customer_id)
    if cached:
        return {"data": cached["data"], "source": "cache",
                "stale_since": cached["saved_at"], "attempts": attempts}
    return {"data": None, "source": None, "attempts": attempts,
            "message": "Live activity unavailable from both APIs and no cached copy exists."}

# The tool result goes to Claude with source/stale_since/attempts, so its answer can say
# "Based on data cached at 08:10 (live systems are unavailable)..." instead of failing or guessing.

Brittle

Primary tool times out → returns "error" → the user gets nothing.

Resilient

Primary times out → secondary endpoint → cache → a clear partial answer that says what it could and couldn't retrieve.

Claude is part of the recovery. When a tool returns a clear, specific error, Claude can often choose another strategy itself: a different tool, a narrower query, asking the user. Anthropic's engineers have reported that simply telling the model a tool is failing, and letting it adapt, works surprisingly well.

Common mistake: waiting until retries are exhausted

Retry logic is standard. The mistake is the information flow around it: retrying silently three times and only then telling Claude, with a summary of three failures it never had a chance to influence.

Wasted timeEvery hidden retry adds latency Claude could have avoided with a different approach.
Lost reasoningClaude isn't just an executor; after one failure it can judge why and what to do next.
Stalled pipelinesA silent loop in one step holds up every step after it.

What to tell Claude after the first failure

  1. What failed: which tool, what it was asked to do, the input.
  2. How it failed: timeout, permission error, empty result, malformed response. Different failures need different responses.
  3. What comes next: whether a retry is planned, how many attempts remain, how long the wait is.

How this fits with section 06

Section 06 said an MCP server or tool may retry a brief transient blip (with backoff) before returning an error, and the Anthropic SDK retries API calls automatically. That's fine for split-second hiccups. The mistake here is a long, silent retry loop that keeps Claude in the dark while it could be choosing a better path. Keep low-level retries short, and surface the failure, with the retry plan, to the reasoning layer early.

Common mistake: marking empty results as successful

The other mistake the Domain 5 overview names. If a lookup couldn't reach its source and returns [] with a success status, every later step treats "couldn't check" as "checked, nothing there". That's field 3 of the error context, and the access-failure vs empty-result distinction from section 06: mark access failures as errors; keep genuinely empty results as success.

Wrong

Right

{"status": "error", "outcome": "access_failure", "retryable": true, "orders": null}
